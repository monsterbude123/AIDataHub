## 项目概述

本项目是一个大数据平台/数据中台的 SDK 式渐构建设，遵循 **DDD 领域驱动设计** + **契约先行（Contract First）** 开发规范，支持多个 AI Agent 并行开发，通过定义清晰的模块边界和接口契约，实现渐构式增量建设。

### 设计原则

1. **DDD 限界上下文拆分**：每个模块对应一个清晰的限界上下文，职责单一无重叠
2. **契约先行**：先定义共享实体和接口契约，再实现，支持并行开发
3. **可插拔**：模块之间仅通过 SDK 接口依赖，实现可替换、可扩展
4. **渐构式建设**：分三个阶段（基础核心→业务能力→治理安全）增量上线

### 边界划分说明

1. **元数据采集职责划分**：
   - `data-integration`：仅负责数据接入时的**初始元数据采集**
   - `metadata`：负责**全生命周期元数据管理**，包括自动采集、订阅更新、版本管理，包含备份恢复
   - 解决了原始需求中"功能重叠"的问题

2. **数据标准化分工**：
   - `data-governance-core`：负责**数据标准定义**（数据元、字典管理）
   - `data-integration`：负责**执行数据标准化处理**（清洗转换、标准映射）
   - 解决了原始需求中"分工不明确"的问题

3. **任务调度分工**：
   - `task-scheduler`：**统一调度中心**，负责所有模块任务的编排、调度、负载均衡
   - 各模块：保留自身任务定义和管理，调度委托给统一中心
   - 解决了原始需求中"缺少统一任务调度"的问题

4. **审批流程分工**：
   - `system-auth`：**统一审批框架**，提供审批模板配置、待办/已办、流程跟踪
   - 各业务模块：使用统一框架实现自身业务审批，无需重复建设
   - 解决了原始需求中"审批流程不完整"的问题

5. **数据服务边界划分**：
   - `data-service`：**技术层面** —— 通用API服务，为任意数据提供技术层面的API发布、流量控制、监控
   - `data-sharing`：**业务层面** —— 跨机构数据共享交换，完整的申请审批业务流程
   - 解决了评审指出的边界模糊问题

6. **数据治理拆分**：
   - `data-governance-core`：核心基础设施（数据地图、标准、模型）
   - `data-governance-ops`：运行操作（质量、标签、血缘）
   - 解决了原单模块过大、粒度不均的问题

7. **系统管理拆分**：
   - `system-auth`：认证授权和审批框架
   - `system-admin`：系统工具类（函数、项目、驱动、日志）
   - 解决了原单模块过大、粒度不均的问题

## 第二阶段：模块功能点定义

逐个模块列出所有内聚功能点，所有功能点严格限定在模块限界上下文内，明确标记为**对外能力**（其他模块可调用）或**内部能力**（仅模块内部使用）。

### 角色 1：项目经理 Agent

**角色定位**：项目整体协调和进度管理负责人

**核心职责**：

1. 跟踪所有模块开发进度，协调多个 AI Agent 并行工作

3. 审核每个模块的接口契约是否符合整体设计
4. 协调解决模块间接口分歧
5. 定期汇总进度，报告阻塞问题

**工作规范**：

- 每日晨会：汇总各模块进度，识别风险
- 每个模块开发完成后进行接口合规模检查
- 发现偏差及时提警，不允许隐性偏离设计

**角色定位**：模块实现负责人

**核心职责**：

1. 根据设计文档中的接口契约，实现模块功能
2. 遵循项目技术栈规范（ts/next）
3. 编写单元测试，保证代码质量
4. 遵循接口契约，不修改已发布的契约定义
5. 需要修改契约必须通过项目经理审批

**工作规范**：

- 契约先行：先保证接口编译通过，再实现业务逻辑
- 依赖 Mock：使用其他模块的 Mock 服务进行联调，不等待依赖模块完成

## 第五部分：并行开发支撑机制

### 1. 如何通过契约 + Mock 支撑多 AI Agent 完全并行开发

**核心机制**：

| 步骤 | 操作                                           | 无需等待               |
| ---- | ---------------------------------------------- | ---------------------- |
| 1    | 定义好共享实体和接口契约                       | 所有模块可同时开始     |
| 2    | 每个模块实现对外接口，依赖其他模块仅通过接口   | 无需等待被依赖模块实现 |
| 3    | 每个模块启动前自动启动所有依赖模块的 Mock 服务 | 本地可独立开发调试     |
| 4    | 所有模块都完成后，一次性去掉 Mock，集成测试    | 最后一步集成           |

**并行度计算**：

- 串行开发：16 个模块 × 平均 2 天 = 32 天
- 并行开发：所有模块同时开始，关键路径是基础核心模块（6个） = 12 天
- 压缩比例：(32 - 12) / 32 = **62.5%**，远超目标 40%

### 2. 版本兼容规则（Schema 修改向下兼容）

为了保证并行开发和迭代过程中的兼容性，强制执行以下规则：

| 变更类型     | 兼容规则                       | 是否需要新版本号       |
| ------------ | ------------------------------ | ---------------------- |
| 新增可选字段 | 必须提供默认值                 | 不需要（兼容旧客户端） |
| 新增必填字段 | 不兼容，需要新接口             | 需要                   |
| 修改字段类型 | 不兼容，需要新接口             | 需要                   |
| 删除字段     | 先标记废弃，保留一个版本后删除 | 需要（次版本）         |
| 新增接口     | 兼容                           | 不需要                 |
| 修改接口语义 | 不兼容，需要新接口             | 需要                   |

**强制规则**：

- 所有共享实体 JSON 序列化必须忽略未知字段，允许新增字段
- 所有接口必须向后兼容，禁止Breaking Change不声明
- 每个模块使用语义化版本号：`主版本.次版本.修订版本`

## 第六部分：渐构式建设路径

### 三个建设阶段

#### 阶段一：基础核心（第 1-2 周）

**包含模块**：

- `data-integration` - 数据接入集成
- `data-service` - 通用数据API服务
- `metadata` - 元数据管理
- `data-organization` - 数据分层组织
- `task-scheduler` - 统一任务调度
- `system-auth` - 身份认证与审批框架

**MVP 交付内容**：

- 可完成数据从数据源接入到存储的全流程
- 可发布数据API服务
- 统一任务调度运行
- 基础权限管理可用
- 最小可用平台可运行

**交付产物**：能够独立运行的最小数据中台核心

---

#### 阶段二：业务能力（第 3-4 周）

**包含模块**：

- `data-operations` - 数据运维监控
- `cost-management` - 成本管理
- `data-sharing` - 数据共享交换门户
- `self-service-analytics` - 用户自助数据分析
- `system-admin` - 系统工具管理
- `system-integration` - 外部系统集成

**MVP 交付内容**：

- 完整的运维监控能力
- 数据共享交换门户可用
- 用户可自助分析数据
- 支持外部系统对接
- 成本统计和配额可用

**交付产物**：具备完整业务能力的数据中台，可支撑业务部门使用

---

#### 阶段三：治理安全（第 5 周）

**包含模块**：

- `data-governance-core` - 数据治理核心
- `data-governance-ops` - 数据治理运行操作
- `data-security` - 数据安全
- `data-lifecycle` - 数据生命周期

**MVP 交付内容**：

- 数据地图可用，支持资产搜索
- 数据质量管理闭环
- 标签和血缘分析可用
- 数据脱敏分级分类完整
- 生命周期管理可用

**交付产物**：完整的企业级数据中台，具备治理和安全能力
