# 附录：并行开发支撑机制与版本兼容规则

> 本附录在阶段 1-4 均完成后生成，用于指导“多 Agent 并行开发、后期一次性集成”的交付方式。

## 1. 并行开发支撑机制（契约 + Mock）

### 1.1 核心结论

只要做到两件事，模块即可完全并行：

- **契约冻结**：阶段 3 的 `phase-3-contracts/*` 作为唯一对接标准
- **Mock 可用**：每个模块都提供对外接口的 Mock 规则（成功 + 关键失败）

### 1.2 并行开发流程（推荐）

1. **写契约**（阶段 3）：定义共享实体、接口、错误码、幂等、Mock
2. **实现模块 A**：只依赖其他模块的 SDK 接口，不依赖其实现
3. **联调时使用 Mock**：
   - A 需要调用 B → 使用 B 的 Mock 客户端/Mock 服务
   - B 尚未完成也不阻塞 A
4. **逐步替换 Mock**：当 B 实现稳定后，用真实 B 替换 Mock
5. **最终集成测试**：所有模块完成后做跨模块链路验收

### 1.3 Mock 的最低要求（门禁）

- 每个对外接口至少具备：
  - **成功返回**（结构符合 DTO）
  - **关键失败返回**（至少 1 个错误码可复现）
- Mock 输出必须包含 `traceId`（便于串联排障）

## 2. 版本兼容规则（Schema / 契约向下兼容）

### 2.1 语义化版本（模块级）

- 版本号：`MAJOR.MINOR.PATCH`
- **MAJOR**：发生不兼容变更（Breaking Change）
- **MINOR**：新增兼容能力（新增接口/新增可选字段等）
- **PATCH**：兼容修复（Bugfix/实现细节）

### 2.2 字段级兼容（共享实体与 DTO）

| 变更类型          | 规则                                      | 兼容性     | 版本建议    |
| ----------------- | ----------------------------------------- | ---------- | ----------- |
| 新增可选字段      | 必须可选（`?`）或有默认值语义             | 向下兼容   | MINOR       |
| 新增必填字段      | 禁止直接新增为必填；应新增新 DTO 或新接口 | 不兼容     | MAJOR       |
| 修改字段类型/语义 | 禁止原位修改；应新增字段并废弃旧字段      | 不兼容     | MAJOR       |
| 删除字段          | 必须先废弃（至少一个 MINOR 周期）再删除   | 不兼容     | MAJOR       |
| 字段重命名        | 视为“新增 + 废弃旧字段”                   | 取决于策略 | MINOR→MAJOR |

### 2.3 接口级兼容

| 变更类型            | 规则           | 兼容性 | 版本建议 |
| ------------------- | -------------- | ------ | -------- |
| 新增接口            | 允许           | 兼容   | MINOR    |
| 新增可选入参        | 允许           | 兼容   | MINOR    |
| 删除接口            | 必须走废弃流程 | 不兼容 | MAJOR    |
| 改变幂等语义/副作用 | 视为语义变更   | 不兼容 | MAJOR    |

### 2.4 废弃（Deprecation）流程

1. 在契约中标注废弃：说明替代接口/字段与迁移路径
2. 至少保持一个 MINOR 版本周期
3. 发布移除版本（MAJOR），并在变更日志中强提示
