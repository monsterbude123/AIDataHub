# Next.js 前端开发规范

专门针对 Next.js 项目开发全流程的标准化开发规范，从项目初始化、路由配置到性能优化、上线提供统一标准。

## 一、核心技术栈选型

以下为生产环境推荐的行业最佳实践技术栈，**必须**遵循该选型要求：

| Technology | Version Requirements | Core Positioning & Usage Guidelines |
|------------|----------------------|-------------------------------------|
| Next.js | 14.x | 必须优先使用 App Router 作为核心路由框架，提供SSR/SSG/ISR/PPR等渲染能力 |
| React | 18.x | 必须使用函数式组件与Hooks范式开发 |
| TypeScript | 5.x | 全项目必须开启强制类型系统，保障类型安全 |
| Tailwind CSS | 3.x | 推荐用于原子化样式开发，配合shadcn/ui使用 |
| TanStack Query | 5.x | 服务端数据请求、缓存与状态管理 |
| Zod | 3.x | 数据输入输出校验，保障接口类型安全 |
| ESLint | 8.x | 代码静态检查，统一代码质量 |
| Prettier | 3.x | 代码格式化，统一代码风格 |
| Jest | 29.x | 单元测试框架 |
| React Testing Library | 14.x | 组件行为测试工具 |
| Playwright | 1.40.x | E2E端到端测试工具 |
| Lucide React | 0.29x | 标准图标库，轻量支持tree-shaking |

## 二、核心开发铁则（最高优先级）

以下规则**必须**强制执行，违反即为不规范：

### 类型安全强制
- **必须**全项目使用TypeScript
- **禁止**使用`any`类型绕过类型检查
- **必须**为所有接口数据定义明确类型

### 成熟方案优先
- **必须**优先使用Next.js原生能力与生态成熟库
- **禁止**自定义实现框架已原生提供的能力

### 状态分离原则
- **必须**由TanStack Query统一管理服务端数据
- **禁止**将服务端数据存入客户端全局状态
- **仅**必要的全局客户端状态才存入全局状态管理

### 组件设计原则
- **必须**遵循单一职责，每个组件只做一件事
- **禁止**出现超过500行的巨型组件，超过必须拆分

### App Router 组件规则
- **必须**默认使用服务端组件
- **仅**在需要交互/浏览器API时才标记为客户端组件

### 可维护性要求
- **必须**清晰命名，目录结构分层清晰
- **必须**抽离公共能力复用
- **禁止**使用无意义缩写与魔法数字

### 可测试性要求
- **必须**在设计时考虑可测试性，依赖注入外部资源
- **禁止**硬编码依赖

## 三、企业级项目目录结构

**必须**遵循以下目录结构组织项目代码：

```
next-frontend-project/
├── app/                      # Next.js App Router 路由入口
│   ├── (routes)/             # 路由分组（同布局/权限路由）
│   │   ├── (public)/         # 无需认证的公共路由分组
│   │   └── (private)/        # 需要认证的私有路由分组
│   ├── api/                  # Next.js API Routes 接口定义
│   ├── layout.tsx            # 根布局
│   └── page.tsx              # 首页
├── components/               # 全局共享组件
│   ├── ui/                   # 基础UI组件（按钮、输入框、卡片等）
│   ├── layout/               # 布局组件（导航、页脚、侧边栏等）
│   └── features/             # 业务通用功能组件
├── lib/                      # 第三方库初始化、工具封装
│   ├── utils.ts              # 通用工具函数
│   └── client-*.ts           # 第三方客户端初始化
├── hooks/                    # 全局自定义Hooks
├── store/                    # 全局客户端状态管理
├── types/                    # 全局通用TypeScript类型定义
├── constants/                # 全局常量定义
├── services/                 # 服务端/接口请求逻辑
│   ├── api/                  # 接口定义封装
│   └── hooks/                # 业务数据请求Hooks
├── styles/                   # 全局样式定义
├── public/                   # 静态资源文件
├── tests/                    # 全局测试相关
│   ├── e2e/                  # E2E测试用例
│   └── unit/                 # 单元测试用例
├── .eslintrc.js              # ESLint配置
├── .prettierrc               # Prettier配置
├── next.config.js            # Next.js配置
├── tailwind.config.ts        # Tailwind CSS配置
├── tsconfig.json             # TypeScript配置
└── package.json              # 项目依赖定义
```

## 四、代码书写规范

### 4.1 命名规范

**必须**遵循以下命名规则：

| 类型 | 命名规则 | 正确示例 | 错误示例 |
|------|----------|----------|----------|
| 组件文件 | 帕斯卡命名法 | `Button.tsx` `UserCard.tsx` | `button.tsx` `user_card.tsx` |
| 工具/类型/常量文件 | 小驼峰命名法 | `utils.ts` `userTypes.ts` | `Utils.ts` `UserTypes.ts` |
| Next.js 页面文件 | 遵循官方规则 | `page.tsx` `layout.tsx` `loading.tsx` | 自定义命名 |
| 变量与函数 | 小驼峰命名法，动词开头 | `getUserInfo()` `isLoggedIn` | `GetUserInfo()` `Isloggedin` |
| 组件与类型 | 帕斯卡命名法 | `UserProfileCard` `type UserInfo = {}` | `userProfileCard` `type userInfo = {}` |
| 全局常量 | 大写下划线分隔 | `const MAX_PAGE_SIZE = 20` | `const maxPageSize = 20` `const MaxPageSize = 20` |

### 4.2 注释规范

- **必须**为公共函数、复杂逻辑、类型定义添加JSDoc注释说明作用与参数
- **必须**为业务特殊规则添加注释说明设计原因
- **禁止**添加无意义的冗余注释（如`// 定义变量a`）
- **必须**为组件对外暴露的props添加注释说明每个属性作用

### 4.3 格式化规则
- **必须**使用2空格缩进，**禁止**使用Tab
- **禁止**单文件超过500行，超过必须拆分
- **必须**遵循以下导入顺序：
  1. React/Next.js核心包
  2. 第三方依赖包
  3. 内部工具/组件/类型
  4. 样式文件
- **禁止**每行超过120字符

### 4.4 禁止实践
- **禁止**在组件中硬编码魔法数字与魔法字符串，**必须**抽离为常量
- **禁止**直接操作DOM，**优先**使用React声明式API
- **禁止**在服务端组件中使用浏览器API
- **禁止**直接使用未校验的接口数据

## 五、核心模块开发规范

### 5.1 路由层（App Router）
- **必须**遵循Next.js文件路由命名规则，使用路由分组拆分不同权限/布局的路由
- **仅**保留路由级别逻辑（元数据、权限校验、路由级数据获取）在路由层，业务逻辑**必须**下沉到服务/组件层
- **推荐**根布局仅保留全局共享布局逻辑，每个路由分组可定义自己的布局

### 5.2 组件层
- **必须**拆分三层组件：基础UI组件、业务通用组件、页面组件
- **必须**基础UI组件不包含任何业务逻辑，可跨项目复用
- **禁止**业务组件跨业务依赖，仅包含对应业务模块逻辑
- **必须**页面组件仅负责组合组件与逻辑，不包含复杂业务实现

### 5.3 服务层
- **必须**所有接口请求逻辑统一封装在`services`目录，**禁止**组件内直接编写请求逻辑
- **必须**为所有接口请求参数与返回值定义TypeScript类型，使用Zod做运行时校验
- **必须**统一处理接口请求错误，**禁止**每个请求重复编写错误处理逻辑

### 5.4 状态管理层
- **必须**服务端数据统一由TanStack Query管理，**禁止**存入Redux/Zustand等客户端状态
- **仅**跨组件共享的客户端状态（主题、登录信息等）才需要全局状态管理，**优先**使用`useState`管理局部状态

### 5.5 工具层
- **必须**通用工具函数统一放在`lib/utils.ts`，业务专用工具放在对应业务目录
- **必须**第三方库初始化统一放在`lib`目录，导出封装后的实例供项目使用

## 六、测试规范

### 6.1 核心测试原则
- **推荐**遵循测试金字塔：单元测试 > 集成测试 > E2E测试
- **禁止**测试框架本身，仅测试业务逻辑与自定义能力
- **推荐**使用真实依赖测试，不模拟内部核心依赖（测试工具提供的测试替身除外）
- **必须**基于用户行为测试，不测试组件内部实现细节

### 6.2 测试环境规范
- **必须**单元测试使用Jest + React Testing Library
- **必须**E2E测试使用Playwright
- **必须**测试环境使用独立Mock接口，不依赖线上环境

### 6.3 测试命名规范
- 测试文件命名：`[模块名].test.ts(x)`，和源文件同目录或者放在`tests`对应目录下
- 测试用例命名：直接描述要测试的行为，例如 `should display user name when user info is loaded`

### 6.4 覆盖率要求
- **必须**核心业务逻辑测试覆盖率不低于80%
- **必须**基础UI组件测试覆盖率不低于70%
- **必须**页面路由与E2E测试覆盖主业务路径

## 七、代码提交规范

**必须**遵循Conventional Commits标准，格式如下：

```
<type>(<scope>): <subject>

<body>

<footer>
```

### 7.1 Type 类型说明
| 类型 | 适用场景 |
|------|----------|
| `feat` | 新增功能 |
| `fix` | 修复Bug |
| `docs` | 文档修改 |
| `style` | 代码格式修改（不影响代码逻辑） |
| `refactor` | 代码重构（不新增功能也不修复Bug） |
| `perf` | 性能优化 |
| `test` | 测试用例修改 |
| `chore` | 构建/工具/配置修改 |

### 7.2 提交要求
- Scope 用于说明代码影响范围（如`user`、`route`），可省略
- Subject **必须**使用祈使语气，首字母小写，结尾不添加句号，长度不超过50字符
- **必须**提交前本地运行ESLint检查，修复所有错误才能提交
- **必须**通过所有单元测试才能提交

## 八、安全与运维规范

### 8.1 配置管理
- **必须**所有环境敏感配置通过环境变量注入，**禁止**提交到代码仓库
- **必须**不同环境（开发/测试/生产）使用不同配置，严格区分

### 8.2 认证与授权
- **必须**认证Token优先存储在HttpOnly Cookie中，**禁止**将敏感Token存在localStorage
- **必须**路由权限校验优先在服务端/中间件完成，**禁止**仅在客户端做权限校验
- **必须**敏感操作添加权限校验，防止越权访问

### 8.3 输入输出校验
- **必须**所有用户输入、接口返回数据做校验，**禁止**直接渲染未校验数据
- **必须**渲染用户输入内容时默认转义，防止XSS攻击

### 8.4 敏感数据处理
- **禁止**在代码中硬编码密钥、API密钥等敏感信息
- **禁止**在日志中输出敏感用户信息（手机号、身份证号等）

### 8.5 部署最佳实践
- **推荐**使用容器化部署，统一Docker镜像构建流程
- **推荐**开启Next.js静态压缩与CDN加速，静态资源托管到CDN
- **推荐**开启核心性能指标监控（Core Web Vitals）与错误监控（如Sentry）
- **必须**生产环境禁止暴露调试信息与源码地图

## 九、禁止实践清单

以下行为**绝对禁止**：

1. **禁止**在Next.js新项目中使用Pages Router开发新功能，**必须**优先使用App Router
2. **禁止**在客户端组件中发起不必要的服务端请求，**尽量**把数据请求放到服务端组件
3. **禁止**滥用全局状态，能局部解决的状态不放到全局
4. **禁止**绕过类型检查使用`any`类型
5. **禁止**将敏感配置提交到代码仓库
6. **禁止**在生产环境开启调试模式
